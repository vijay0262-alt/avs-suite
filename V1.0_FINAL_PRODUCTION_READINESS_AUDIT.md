## 4. End-to-End Workflow Audit

### Canonical Remediation Flow (verified)

```
User clicks "Review & Optimize" / "Review & Fix"
  → useSmartOptimizationPlan / useSecurityRemediationPlan / useDashboardOptimizationPlan
    → scan_core.smart_optimization.plan / scan_core.security_remediation.plan / scan_core.dashboard_optimization.plan RPC
      → Backend creates ActionPlan (backend-authoritative)
  → PlanReviewView displays plan details (read-only, from backend)
    → Stale-plan warning if is_stale=true
    → User clicks "Approve & Fix"
  → ResultsView: prepare → validate → approve → execute
    → scan_core.remediation.prepare RPC
    → scan_core.remediation.validate RPC
    → Explicit "Approve & Fix" button (disabled unless valid)
    → scan_core.remediation.execute RPC (with approval_token, mode=live)
      → SafetyGate validation
      → RemediationCoordinator execution
      → ExecutionLedger idempotency
      → Backup before deletion
      → Post-execution verification
  → Progress polling (scan_core.remediation.status)
  → Completion or failure
  → Rollback available if supported
```

## 16. Fixes Applied

### Fix 1: RemediationCoordinator cancellation registration race

**Root cause:** `RemediationCoordinator.execute()` registered the cancellation token in `self._tokens` AFTER completing setup work (`_load_plan()`, `is_stale()` check, approval check, lock acquisition). If `coordinator.cancel()` was called during this setup window, it found no token in `self._tokens` and returned `False` — the cancellation was silently lost.

**Impact:** Under heavy load (full test suite with parallel workers), the setup phase could exceed 50ms, causing `test_partial_execution_and_recovery` to fail with `cancelled=0`. In production, a user cancellation request during execution setup would be lost.

**Fix:** Move token registration to occur under the lock, BEFORE any setup work. This ensures `cancel()` can find the token at any point after `execute()` is called.

**Files changed:**
- `backend/src/avs_backend/scan_core/orchestration/remediation.py` — moved `self._tokens[request_id] = token` into the `with self._lock` block, before `_load_plan()` and pre-execution checks
- `backend/tests/test_sc8c6_remediation_coordinator.py` — added `test_cancel_registered_before_setup_completes` regression test that deterministically verifies cancellation with a 1ms delay (fast enough to land during setup on any machine)

**Why the fix does not compromise production behavior:**
- The token is still associated with the request before any execution work begins
- The `_active` set and `_tokens` dict are still managed under the same lock
- The `finally` block still cleans up both `_active` and `_tokens`
- Stale-plan and approval checks still run after token registration — they return rejected summaries without executing, and the `finally` block cleans up the token
- No `sleep()` or artificial delay was added to production code
- No cancellation semantics were weakened
- No executor, SafetyGate, ActionType, or scan_core architecture was modified

**Verification:**
- Race reproduction script: 20/20 races before fix, 0/20 after fix (with 1ms cancel delay)
- Failing test: PASS
- New regression test: PASS
- Full SC-8C6 file: 17/17 PASS
