## Architecture & Data Flow

```
ScanResult
    ↓
ActionPlan (persisted via ActionPlanRepository)
    ↓
RemediationCoordinator.prepare(plan_id) → RemediationPreview
    ↓
RemediationCoordinator.validate(plan_id) → dry-run validation
    ↓
explicit approval token + RemediationCoordinator.execute(plan_id, mode="live")
    ↓
load plan, rebuild typed preconditions, fresh context per action
    ↓
DefaultExecutor.execute(ExecutionRequest)
    ↓
ExecutionSummary + persisted status/audit
    ↓
RemediationCoordinator.rollback(execution_id) → RollbackSummary
```

The coordinator is pure orchestration: it does not call `os.remove`, `shutil.rmtree`, `winreg` writes, `subprocess`, or any direct destructive APIs. All mutations continue through the existing target executors (`FilesystemExecutor`, `RegistryExecutor`, `BrowserExecutor`, `StartupExecutor`) invoked by `DefaultExecutor`.

## Coordinator API

- `prepare(plan_id)` — returns a non-mutating `RemediationPreview` with request/approval tokens, counts, affected targets, and warnings.
- `validate(plan_id)` — dry-runs the plan through `DefaultExecutor` and returns a `RemediationValidation`.
- `execute(plan_id, request_id, approval_token, mode="live", ...)` — executes a plan after explicit approval and fresh re-validation.
- `get_status(execution_id)` — loads persisted `ExecutionRepository` audit data and returns `RemediationExecutionStatus`.
- `cancel(execution_id)` — cancels an in-flight execution via its `CancellationToken`.
- `rollback(execution_id)` — restores completed filesystem actions using `BackupManager` records when the target has not been modified.

## Approval Boundary

Live execution requires an explicit `approval_token` generated by `prepare()`. The coordinator rejects live execution when:
- `approval_token` is missing or empty.
- `ActionPlan` is stale (older than TTL / `is_stale()`).
- Plan is already active or has reached a final state.
- Actions are `blocked`, `not_fixable`, `review_required`, `missing_target`, or `locked_target` (enforced by `SafetyGate`).
- Fresh execution context cannot be obtained.
- Typed preconditions fail (target missing, size/time changed, identity mismatch, unsafe path, symlink/junction, etc.).

## Preview Workflow

`prepare()` loads the persisted `ActionPlan` and returns:
- total action count and per-type counts
- estimated affected size
- safety-state and fixability counts
- rollback/backup support flags
- warnings for any `blocked`, `review_required`, or non-actionable actions
- a `request_id` / `approval_token` pair

Preview never modifies the system.

## Fresh-Context Workflow

For every live action, the coordinator supplies a `context_provider` callback that re-reads current filesystem state and returns a `FilesystemContext` dictionary with:
- `exists`, `accessible`, `locked`
- `canonical_path`, `asset_id`
- current `size`, `modified_time`
- `is_symlink`, `is_junction`, `is_reparse_point`
- `safety_level`

The serialized scan context is not used as proof of current state. `DefaultExecutor` and `SafetyGate` then evaluate typed preconditions before any target executor runs.

## Execution State Machine

The coordinator reuses the existing `scan_core/execution/state_machine` states:

- `planned`, `running`, `completed`, `failed`, `cancelled`, `rolled_back`
- `dry_run`, `approved`, `rejected`, `skipped`, `requires_review`

The user-specified `VALIDATING` and `PARTIAL` states are not separate persisted values because the lower-layer state machine does not define them:
- The validation phase is represented by `validate()` returning a `RemediationValidation` object; it is not persisted as `VALIDATING`.
- Partial execution is represented by a terminal summary where `cancelled`, `failed`, or `rejected` is non-zero and `completed < total`. The persisted `ExecutionSummary` and `get_status()` expose those counts directly.

Invalid transitions are rejected by `ExecutionRepository.update_request_status()`.

## Persistence & Recovery

- `ActionPlan` loaded from `ActionPlanRepository`.
- `ExecutionRequest`, action results, and `ExecutionSummary` persisted through `ExecutionRepository` into the existing `MetadataDatabase` (no second database).
- `DefaultExecutor` internally swallows persistence errors; the coordinator adds a `_finalize_status()` backstop that re-persists a ledger-free, JSON-serializable summary and updates the request status. This prevents a completed `ExecutionSummary` in memory from leaving the persisted request stuck in `running`.
- Recovery after restart can load the persisted `ExecutionRequest` and completed action IDs from the `ExecutionLedger`/`ExecutionRepository`. The current coordinator stores in-memory token/active sets; long-running recovery across processes relies on the persisted `execution_requests` table and `get_completed_action_ids()`.

## Concurrency & Idempotency

- In-memory `_active` set and `threading.Lock` protect against duplicate execution of the same `request_id` in a single process.
- `ExecutionRepository` constraints prevent duplicate final requests/persisted statuses.
- `ExecutionLedger` seeds from previously completed action IDs to avoid re-executing completed work.
- True distributed locking is not claimed; the coordinator documents single-process behavior and uses persisted state for cross-process idempotency.

## Rollback Behavior

`rollback(execution_id)`:
- loads the persisted `ExecutionSummary`
- only attempts restore for `status == "completed"` actions that have a `backup_identity`
- re-reads the current target before restoring
- refuses to overwrite a target whose current content differs from the backup (hash comparison for files, empty-directory check for directories)
- uses `BackupManager.restore(record)` and `RegistryBackup.restore(record)` without duplicating low-level backup logic
- persists a `RollbackSummary` with per-action results
- prevents duplicate rollback (a second call finds no unrolled completed actions, returning zero successful results)

## Security Guarantees

- No direct destructive filesystem/registry/browser/startup code in the coordinator.
- `SafetyGate` final authority is preserved.
- Typed preconditions (`TargetExists`, `TargetAccessible`, `TargetNotLocked`, `TargetIdentityMatches`, `SizeMatches`, `PathWithinAllowedScope`, `NotSymlink`, `SafetyLevelValid`, etc.) are rebuilt and re-evaluated at execution time.
- Loaded plans cannot bypass preconditions: placeholder `_PersistedPrecondition` records are replaced with freshly built typed `PreconditionSet` objects before `DefaultExecutor` runs.
- Path validation, TOCTOU re-verification, and post-execution verification remain in `FilesystemExecutor`.
- Audit output (`RemediationExecutionStatus.to_dict()`) exposes only counts, status, and IDs; no raw file contents, usernames, or passwords.

## Known Limitations

- `VALIDATING` and `PARTIAL` are not independent persisted states; they are expressed as coordinator-level phases and partial result counts on top of the existing lower-layer state machine.
- `DefaultExecutor` swallows its own persistence errors; the coordinator adds a best-effort backstop but does not fundamentally change `DefaultExecutor`.
- In-memory `BackupManager` records are reconstructed for rollback from persisted `ExecutionSummary` data; full backup metadata integrity is limited to what the executor stored in `backup_identity` and `backup_location`.
- Registry, browser, and startup rollback rely on the existing executor-level `RegistryBackup`/`BrowserBackup`/`StartupBackup` facilities; the coordinator does not add new low-level restore logic.
- Cross-process concurrency protection depends on SQLite-level persistence constraints; in-process locking is a single-process guard.
