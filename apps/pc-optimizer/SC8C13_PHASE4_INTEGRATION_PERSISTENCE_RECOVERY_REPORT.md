## 1. Objective

Validate and harden that Dashboard Optimization behaves correctly across:

- application restart

- stale plans
- completed actions

- failed execution

**Phase 4 required no production architecture changes; the canonical SC-8C10 persistence/recovery model already covers Dashboard Optimization.**

Dashboard plans are persisted via `ActionPlanRepository`, hydrated via `plan_details` RPC, and executed via `RemediationCoordinator` — all by `plan_id`. The entire persistence/recovery architecture is `plan_id`-based and applies uniformly to all plan types (scan, Smart Optimization, Security Remediation, Dashboard Optimization).

```

→ orchestrator.get_plan_details(plan_id)
→ ActionPlanRepository.load(plan_id)
→ ActionPlan with findings, statistics, is_stale
→ PlanReviewView renders plan
→ ResultsView (no auto-execution)
```

## 5. Active vs Persisted Precedence

### Principle

1. **Active state wins** — `unifiedScanState` (in-memory) takes precedence
2. **Persisted state is fallback** — `scan_core.scan.latest` RPC used when no active session
3. **Empty history gives idle state** — Safe fallback when no data exists

### Frontend tests

| Test | Verification |
|---|---|
| `active in-memory session hides persisted history for Dashboard` | Active session displayed, persisted ignored |
| `persisted history is used when no active state exists` | Persisted scan shown when no active session |
| `empty history gives idle state` | Safe idle state when no data |

### Implementation

`DashboardScanStatusCard` checks `unifiedScanState.getLatest()` first. If an active session exists, it displays that. If not, it calls `scan_core.scan.latest` RPC to load persisted history. This is the existing SC-8C10 behavior — no Dashboard-specific changes needed.

## 7. Stale Plan Behavior

### Backend mechanism

`ActionPlan.is_stale()` (line 619 of `action.py`):
```python
def is_stale(self) -> bool:
    reference = self.snapshot_timestamp or self.generated_at
    if reference is None:
        return False
    age = (datetime.now(UTC) - reference).total_seconds()
    return age > self.snapshot_ttl_seconds
```

Dashboard plans have `snapshot_ttl_seconds=3600` (1 hour), same as Smart Optimization.

`RemediationCoordinator.execute()` rejects stale plans at line 113.
`RemediationCoordinator.prepare()` includes stale warnings at lines 403-404 and 419.

### Frontend behavior

`PlanReviewView` shows `plan-review-stale-warning` when `isStale` is true. The user can see the plan but must be cautious. Execution is blocked by the backend.

## 9. Partial Execution Recovery

### Mechanism

`ExecutionRepository.get_completed_action_ids(plan_id)` returns only actions with `COMPLETED` status. When execution is interrupted:

1. Completed actions are persisted in `execution_results` table
2. On restart, `get_completed_action_ids()` recovers them
3. `ExecutionLedger.seed_completed()` marks them as done
4. `Executor._execute_single_action()` skips them (idempotency check)
5. Remaining actions can be executed by explicit user action

No automatic resume occurs. The user must explicitly initiate re-execution through the canonical flow.

### Test coverage

## 10. Rollback/Backup Recovery

### Mechanism

`BackupManager` records backups for actions with `rollback_supported=True`. Rollback is triggered via `scan_core.remediation.rollback` RPC, which requires explicit user action.

### Verified behavior

| Test | Verification |
|---|---|
| `rollback is not automatically triggered during hydration` | No rollback RPC during hydration |
| `does not automatically rollback after restart` | No rollback RPC after restart |

### Dashboard-specific notes

Dashboard Optimization actions are primarily `DELETE_FILE` and `DELETE_DIRECTORY` operations. The Phase 2 adapter sets `rollback_supported` based on the action type and target. The `rollbackAvailable` field in the frontend payload is set to `false` by the serializer, but the backend adapter makes the final determination based on `ActionType` and `SafetyGate` evaluation.

Rollback remains explicit — no automatic rollback after restart, hydration, or any other event.

1. **`ActionPlanRepository`** persists all plans by `plan_id` — Dashboard plans have unique UUIDs

## 18. Remaining Limitations

1. **Legacy `dashboard.optimize.execute` RPC retained** — Phase 5 owns final deletion. The production UI no longer invokes it (disconnected in Phase 3).

2. **`dashboardService.executeOptimize` retained** — Retained for backward compatibility, disconnected from production UI. Phase 5 owns removal.

3. **`DashboardViewModel.executeOptimize` retained as no-op** — Deprecated in Phase 3. Phase 5 owns removal.

4. **`OneClickOptimize.tsx` retained** — Retained with non-destructive labels. Not imported by `DashboardPageV2`. Phase 5 owns removal.

5. **`executionHandler.ts` in smart-optimization-ai** — Contains legacy `dashboardService.executeOptimize()` calls. Not reachable from production UI. Phase 5 owns cleanup.

6. **Flush DNS and Trim Memory remain `NOT_FIXABLE`** — These operations are classified as `OUT_OF_SCOPE` by the backend adapter. They appear in plan review as non-executable items but cannot be remediated through `scan_core`.

7. **`canonical_path` in persisted `FilesystemActionTarget`** — The persisted `ActionPlan` legitimately stores `canonical_path` in `FilesystemActionTarget` for execution purposes. The privacy boundary is at the RPC response level (`orchestrator.get_plan_details` strips it to `""`), not the persistence level. This is by design — the backend needs the path to execute, but the frontend never sees it.
